# Harvest A1-C — Storage, API & Operations Contract

Status: **Detailed design for review** (2026-11-08). This freezes the intended V0.1 SQL/API/operations boundaries; implementation code and final numerical defaults remain subject to disposable-DB integration and measured budget validation. It complements [A1 Baseline](./harvest-a1-architecture-engineering-baseline.md), [A1-A](./harvest-a1-a-provider-resource-transport.md), [A1-B](./harvest-a1-b-distributed-scheduling-execution.md), and [A1-P](./harvest-a1-proxy-egress-contract.md).

## 0. Scope and guarantees

Harvest is a standalone product, **not** the GoFurry business data store, the CN/INTL synchronization service, an infinite archival crawler, or an open HTTP proxy. Harvest owns a dedicated PostgreSQL 18 database and a versioned private-first API. Consumers (GoFurry CN initially) map Harvest observations to their own local business schemas, then own their own regional publishing/sync. No direct consumer SQL access to Harvest.

V0.1 must work on a shared 4C8G VPS with a single server and local Worker, but the same contract must run with a remote Worker over Tailscale. Default operation is low-frequency and bounded in CPU/IO, response bodies, history and proxy traffic. On uncertainty, preserve last-known-good and report incomplete/failed collection rather than manufacture a healthy observation.

Go 1.27.3 native UUIDv7 for all entity PKs, PostgreSQL `uuid`; numeric revision, small counters, fixed-point token balances and stream positions are **not identity PKs**, and may be incremented. No auto-increment identity columns, ORM, implicit migrations, Redis/Kafka queue or new microservice.

## 1. PostgreSQL ownership and relational schema

Use one owned `harvest` schema within Harvest's own database (for readability and permissions; schema naming is not a cross-service boundary). Goose migrations are the sole DDL authority. sqlc + pgx/v5 owns all stable operational SQL; explicit pgx transactions and documented exceptional SQL only where necessary. No runtime schema create/repair.

Proposed core tables; exact columns/check constraints and indexes are formalized in the first implementation PR, with the below identities/invariants mandatory:

| Table | Key fields and invariants |
|---|---|
| `harvest.targets` | `id uuid PK`, `provider`, `resource_type`, `external_key`, `access_namespace`, status/time; UNIQUE(provider,resource_type,external_key,access_namespace). Never merge `www`/apex or origins. |
| `harvest.schedules` | `id uuid PK`, target FK, capability+schema, canonical params/fingerprint/scope, interval or UTC cron, anchor, next_due, policy, revision, enabled/paused. CAS revision for operator edits. |
| `harvest.jobs` | `id uuid PK`, target FK, optional schedule FK+revision+scheduled_for, cause, request fingerprint, immutable canonical params, authorization scope, available_at/deadline, priority/state, attempt/max_attempt, lease_generation, accepted_result_hash; uniqueness per schedule/revision/slot and bounded active dedupe for compatible requests. |
| `harvest.attempts` | `id uuid PK`, job FK, worker FK, fencing generation UNIQUE(job_id,generation), started/renewed/lease_until/ended, status, sanitized error, accepted payload hash and immutable acceptance receipt. |
| `harvest.workers` | `id uuid PK` per boot, authorized principal ID, capabilities/schema versions, *nonsecret* egress profiles/regions, capacity, last_seen, draining/status. Periodic UPDATE of same row; no append-only heartbeat table. |
| `harvest.quota_buckets` | scoped key PK or UUID PK + unique natural key, refill/update clock, token allowance, concurrency limit and cooldown. Database-time atomic reservation; no network IO under row lock. |
| `harvest.quota_permits` | `id uuid PK`, bucket/attempt/worker, expiry and release/consumption state; only where required for concurrency or idempotent permit accounting, with aggressive bounded pruning. Do **not** create an immutable full request-log row for every HTTP operation. |
| `harvest.current_results` | composite UNIQUE(target_id,capability,output_schema,canonical_scope), latest successful value and hash, observed_at, received_at, revision. A failed/uncovered segment cannot overwrite it. Raw payload not stored by default. |
| `harvest.observations` | `id uuid PK`, target, capability/schema, canonical_scope, attempt FK where retained, observed/received times, state, bounded typed data/hash/provenance. Historical observation is not a full Job log; retention is per capability. Do not use ON DELETE CASCADE for the important current-result or delivery identity. If attempts expire first, observation lineage must remain readable through immutable nonsecret identifiers without requiring that FK to survive. |
| `harvest.change_heads` | one durable row per authorized stream (`stream_key` PK), `last_committed_position bigint`, `min_available_position bigint`, data epoch. Position is **not** generated by sequence. |
| `harvest.change_events` | PK(stream_key,position), logical event UUID, target/capability/scope, action (`upsert` / `withdraw` / `sample`), reference/result version, committed_at. Event does not need to duplicate large result bodies. |
| `harvest.consumers` | `id uuid PK`, service principal/allowed stream(s), last acknowledged position and last_seen, reset-required state. A consumer acknowledges **after local durable application**; reads do not implicitly acknowledge. |
| `harvest.maintenance_state` | small checkpoint/config-health state for batched retention and safety diagnostics, not a generic tasks/DAG subsystem. |

The above is intentionally ~12 small tables, not one table per Provider, per endpoint, or per business field. Provider-specific typed current/historical results are carried in schema-versioned bounded `jsonb` only where appropriate; high-frequency numerical measurements can use compact typed numeric columns or an expressly narrow time-series table if profiling demonstrates material savings. Do not put images/videos/large website HTML into PostgreSQL.

Important constraints and indexes:

- FK and unique natural identity for Target; schedule slot uniqueness; Attempt fencing uniqueness; one active lease per Job enforced by Job row lock; per-scope current result uniqueness; stream (key,position) uniqueness; Consumer scope authorization. Use CHECK constraints for statuses, durations, positive limits and JSON bounds at API/application boundary.
- Partial indexes for due `queued/retry_wait` Jobs ordered by priority/available_at; live lease expiration; upcoming schedule due; observation (target,capability,scope,observed_at DESC) and retention timestamp; change (stream_key,position); consumer acknowledgement. Inspect `EXPLAIN (ANALYZE, BUFFERS)` with realistic cardinalities.
- High-frequency mutable worker/quota state is not mixed with long-lived immutable observations. Use UTC `timestamptz`, PostgreSQL clock for lease/refill/commit-sensitive operations, explicit transaction isolation (READ COMMITTED + targeted row locks is the V0.1 default).
- No speculative partitioning of every table. Add monthly partitions **only** for proven high-volume, time-bounded append tables when measured delete/IO pressure justifies them; PostgreSQL partition uniqueness/FK constraints need deliberate design.

## 2. Atomic acceptance, current data and scope

A1-A's per-segment states are normative: `present`, `confirmed_empty`, `not_modified`, `unavailable`, `invalid`, `not_covered`. Genuine zero is not failure. Result receipt is deduplicated using (Job, Attempt, lease generation, canonical payload hash) under a Job lock.

Finalization transaction:
1. Lock Job; validate Attempt current fencing, valid lease and Job state (A1-B). An exact retry of an already accepted result returns its stored receipt; a conflicting replay is rejected.
2. Validate typed capability schema, authorization namespace, source/proxy-semantic scope, size and payload hash. Only validated success/definitive empty segments update `current_results` and appropriate `observations`. Never blank unrelated scopes due to partial upstream failures.
3. Generate `change_events` only according to capability event policy: semantic changed-current upserts/withdrawals; meaningful point-in-time numerical samples get `sample` events if the authorized consumer contract requests them. A routine unchanged details probe should not create another large identical payload/event. Update last-observed freshness separately without implying content changed.
4. Commit Attempt/Job state, scoped current/observations, and all delivery events in the **same SQL transaction**. If any part fails, roll back all changes.

An upstream deletion is not inferred from a transient 404 or malformed response. A `withdraw` is accepted only with a capability-specific authoritative disappearance rule. Consumer-side business deletion/moderation is never Harvest's duty.

## 3. Commit-safe incremental stream (critical correctness contract)

**Forbidden:** using UUIDv7 order, `created_at` timestamps, `nextval()` or an ordinary auto-increment `bigserial` as a cursor while assuming those values match SQL commit order. These can let a consumer skip a late-committing earlier event.

V0.1 design: one *serialized transactional stream ledger* per authorized stream.

- Every result-writing transaction that emits changes locks its `harvest.change_heads` row `FOR UPDATE`, obtains `last_committed_position`, allocates consecutive new positions by updating that row, inserts change-event rows, and commits **while holding that row lock**.
- A second transaction targeting the same stream must wait until the first commits or rolls back. On rollback, both head increment and events roll back; no published hole. Once an API returns head position N, no transaction can later commit a missing position <=N for that stream.
- Lock order must be globally documented: Job -> Attempt -> current/observations -> stream head -> stream events. Multi-stream result commits (if needed) lock stream heads in lexical stream-key order to prevent deadlocks. Do not expose partially committed change batches.
- Stream keys separate allowed public observations and any credential/private data scope; no cross-namespace leak. Default stream for shared public data is singular and can be monitored for contention. Adding sharding or new stream keys is explicit schema/protocol evolution, not silent replay reordering.
- Read `GET /api/v1/changes?stream=...&after=...&limit=...`: returns only committed events with positions >after, ordered ascending, plus `next_cursor`, `head_cursor`, `min_available_cursor` and `has_more`. Limits: 50 default / 200 maximum (candidate). Opaque cursor can encode version, epoch, stream key, position, be validated and checked against principal scope.
- `ACK /api/v1/consumers/{id}/cursor` (exact HTTP method chosen with API routes below) advances the durable acknowledged position only after the consumer's own DB commit. Reject ACK beyond committed head or ACK for another scope; monotonic max. A successful read does not ACK.
- Retention can normally prune safely acknowledged rows but **does not hold all events forever** for an indefinitely offline consumer. Each stream has a configurable bounded retention horizon/size; before a destructive prune that would overrun a consumer's cursor, mark that consumer `reset_required` with a reason, and reject continued stale-cursor polling (HTTP 410 with machine-readable `cursor_expired`), not silent skipped events.
- Maintain `min_available_position` accurately on prune; `after == min_available_position - 1` is acceptable (subject to stream epoch), older is expired. Page and cursor values are stream-scoped and nonforgeable as to access control; cursor opacity alone is not authentication.

### Baseline/resume protocol (consumer recovery)

1. Authenticated consumer starts a reset and records the **committed head** as `baseline_cursor`. It obtains a stable `snapshot_id`/epoch and a keyset-paged export of authorized **current** results. Pagination by immutable Target + Capability + Scope identity, never OFFSET; export is bounded by pages and a snapshot expiry. The snapshot API must provide a well-defined consistent view **or** support the 'baseline then replay' reconciliation described next.
2. Simple V0.1 approach: choose a committed head at reset start; allow a *live* keyset snapshot while concurrent writes continue; after applying all snapshot pages, **replay changes strictly after the recorded baseline head** to reconcile concurrent updates/deletions. This requires complete coverage of all current identities, no removal of changes after the baseline before replay, and upsert/withdraw events sufficient to reconcile rows that vanished during pagination. Consumer must stop and restart baseline if replay horizon expires before completion.
3. Consumer stores its imported data and next cursor atomically in its own DB as much as its architecture permits. `ACK` is a later advisory server-side step; retry on failed ACK. Never flip to a clean state until baseline+replay finishes.
4. Snapshot authorization and scope are fixed for the reset; any permission/policy change invalidates the reset. For private data, enforce per-consumer visibility on every page.

Snapshot replication is a synchronization mechanism for acquisition observations **only**; it does not become GoFurry's CN->INTL business synchronization protocol. For now GoFurry CN is the principal Harvest data consumer.

## 4. Retention, cost and pruning

Storage is **bounded by design** with both age and (where practical) count/byte ceilings. The following are **V0.1 initial configuration candidates**, not truth about every Provider or fixed future product defaults:

| Class | Initial behavior |
|---|---|
| Targets/Schedules | Retain while managed, archive explicitly; avoid deleting a target just because its schedules pause. |
| Current successful results | Keep last-known-good; small indexable projection, only changed payload replaces it. Prune only after explicit Target removal/retirement and dependent consumer semantics checked. |
| Completed Job/Attempt diagnostics | 30 days (optionally shorter for noisy successful jobs); active leases and cancellation receipts must never be deleted. |
| Worker presence | One row per instance boot, update in place; prune retired/offline instances after safe Job/Attempt lineage handling, e.g. 7-30 days. |
| Web HTTP/DNS/TLS | Latest + semantic change history, not full repeated HTML. Optional bounded periodic measurements if consumers require them. |
| Steam details/news | Current scoped normalized result; history of meaningful changes with cap. Store provenance/payload hash, not every identical raw response. |
| Steam players | Raw point-in-time samples about 30 days; optional daily aggregates about 180 days only if explicitly useful. Never manufacture missed samples. |
| Optional raw snapshots | Off by default; if enabled, per-capability age/count/byte ceiling, with strict sensitive-data redaction policy; no media binaries. |
| Change delivery log | Initial ~14-day horizon with explicit storage-budget alarm and stale-consumer reset. If consumers need more recovery margin, adjust measured config; never guarantee unlimited backlog. |
| Quota permits/health/request diagnostics | Minimal durable active reservations; short bounded retention and aggregated, nonsecret counters; no per-request immutable proxy logs. |

Never delete current-result data before the downstream reset protocol can obtain it. A consumer lag beyond a bounded log budget triggers **visible reset**, not hidden loss. Storage-pressure order: prune already-safe expired raw/diagnostics first, then compact eligible history/aggregates, then mark a lagging consumer reset-required before changing delivery `min_available_position`. Never delete active leases, latest-good, unmigrated changes, or important historical coverage merely to silence a warning.

Pruning:
- Server-controlled periodic **bounded batch transactions** with explicit max rows/duration and checkpoint. No automatic pruning inside every synchronous result insert.
- Use row-locked/lease-safe eligible scans and stable keyset deletion. Verify original parent/current identities and FK implications; no blanket CASCADE.
- Maintenance must not overlap destructively with another controller; short transactional lock/maintenance state protects each step, with crash-safe resumption.
- Aggregate/storage metrics from PostgreSQL relation sizes and estimated row counts; report pruning age, backlog, largest tables, database footprint and old-consumer/reset status. Resource values are estimated, not exact billed cost.
- Start unpartitioned to avoid new operational complexity. Consider monthly partitioning for raw samples/change events only if profiling demonstrates high-volume retention pressure. PostgreSQL partition removal is efficient but constraints and baseline consumer replay must be considered.
- Periodic backup/restore test is required before first production import; PostgreSQL remains operator-owned. Do not invent disaster recovery by storing the sole valid observation only in an expiring queue.

### Payload and pressure budgets

Default candidates must be checked with real Steam details fixtures and Web probes: each normalized segment <=512 KiB, one Job response <=4 MiB, optional raw snapshot <=1 MiB, bound network response body in the provider/transport (actual upstream requests may require a higher temporary in-memory decode bound). Failure of size validation yields a typed `result_too_large`, never partial DB corruption. Large binary/media assets are referenced by URL, not embedded.

For a shared 4C8G host, start with a deliberately small pgxpool (e.g. 2-5 connections for Server), low local Worker concurrency (e.g. 2-4), low-frequency polling with backoff and jitter, limited sync pages and cleanup batches. These are starting tunables, **not capacity claims**; benchmark against the real host's other processes before production. Expose measurable DB connections, transactions/sec, query p95, CPU/heap, wal/DB size growth, queue age and change-head lock contention. If per-network-request DB permit round trips prove expensive, consider small fenced quota grants in a separate measured phase, not an unsafe unbounded local bypass.

## 5. Versioned HTTP routes, explicit router ownership

`routers/router.go` defines route groups/middleware; `routers/url.go` defines the exact method/path mapping; `routers/health.go` provides probes; handlers/services/SQL live outside routers. Split registration between consumer/admin endpoints and authenticated private Worker endpoints; route inventory tests detect accidental unreviewed paths. Do not expose raw SQL or arbitrary open-proxy requests.

### Consumer/operator API (private-first `/api/v1`)

| Method/path | Purpose |
|---|---|
| `GET /api/v1/providers` | Compiled provider/capability discovery, schema IDs and transport requirements; no credentials. |
| `GET /api/v1/targets`; `POST /api/v1/targets` | Keyset list/filter and idempotent canonical target registration. |
| `GET /api/v1/targets/:id`; `PATCH /api/v1/targets/:id` | Read and status/archive edit with revision guard. No implicit hard-delete. |
| `GET /api/v1/schedules`; `POST /api/v1/schedules` | List and create schedules with validated UTC interval/cron and request scope. |
| `GET /api/v1/schedules/:id`; `PATCH /api/v1/schedules/:id` | Read/edit/pause/resume; revision optimistic concurrency. |
| `POST /api/v1/jobs`; `GET /api/v1/jobs/:id` | Enqueue manual or referenced retry Job; read durable status/sanitized summary. Use `Idempotency-Key` for submit. |
| `POST /api/v1/jobs/:id/cancel` | Request cancellation; accepted or already-terminal explicit response. |
| `GET /api/v1/observations/current`; `GET /api/v1/observations/history` | Scoped latest-good and bounded historical results; never raw credentials or unrestricted payload dumps. |
| `GET /api/v1/changes`; `GET /api/v1/snapshots/current` | Authorized commit-safe incremental stream and scoped keyset baseline. |
| `POST /api/v1/consumers/:id/ack` | Monotonic server-side acknowledgement; consumer must first durably commit locally. |
| `GET /api/v1/operations/status` | Authenticated queue/worker/quota/egress/storage summary, compact and sanitized. |

Default paginated list 50, hard maximum 200 entries (candidate); strict validation of query params, JSON versions, body-size/rate caps, authorized target namespace and response budget. Route and request types are versioned; preserve existing v1 fields and additive compatibility unless explicit new version. Normal errors use stable `code`, `message`, request ID and retryable semantics; distinguish 400 bad input, 401 unauthenticated, 403 forbidden, 404 absent, 409 revision/idempotency conflicts, 410 expired cursor, 429 rate, 503 unavailable, 507 optional budget pressure only when meaningfully distinguishable. Use UTC RFC3339 timestamps and UUID strings over JSON.

### Private Worker protocol (`/internal/v1`)

| Method/path | Purpose |
|---|---|
| `POST /internal/v1/workers/register` | Authenticate configured worker principal, bind one ephemeral instance UUID, announce verified capability/egress profiles. |
| `POST /internal/v1/workers/:id/heartbeat` | Bounded instance heartbeat, draining/capacity/capability summary; returned drain/cancel hints. |
| `POST /internal/v1/workers/:id/claim` | Bounded long-poll/claim, current Job/Attempt/fencing and nonsecret request scope. |
| `POST /internal/v1/attempts/:id/renew` | Renew valid leased Attempt by job/worker/generation and DB time. |
| `POST /internal/v1/attempts/:id/complete` | Validate and atomically accept result, replay-safe receipt or stale fence rejection. |
| `POST /internal/v1/attempts/:id/permit` | Issue per-outbound-operation quota permit for the authorized upstream/egress bucket(s). |
| `POST /internal/v1/permits/:id/finish` | Release active concurrency accounting or record sanitized usage; idempotent. |

Do not pass database URLs, proxy credentials, OAuth secrets, raw consumer keys or entire source snapshots over claim responses. If a Provider requires a secret, it is resolved by the authorized Worker's local config, referenced by stable `credential_ref` only. Explicit namespace/worker authorization is enforced even over Tailscale.

No WebSocket, external public webhook or separate dashboard is required for V0.1. CLI can exercise the same service APIs; optional minimal console is a later surface, not part of the foundation's proof.

## 6. Service authentication and isolation

Start with a small explicit YAML registry of service principals and credentials: consumer reader/operator/writer versus worker runtime are different scopes. Tokens are random high-entropy secrets in ignored local YAML with restrictive file permissions, verified constant-time (or hashed and constant-time comparison). Service principal defines allowed namespaces, Providers, capability families, quota/egress profiles and read/write/worker actions; do not build a human account/OAuth platform. Credential rotation is an operator action and may require a restart in V0.1.

Private/Tailscale ingress is necessary for default deployments, but is **not** authentication. Nginx must not publicly proxy `/internal/v1/*` or administrative endpoints. Validate the trusted proxy chain exactly; never broadly trust all forwarded IP headers. No browser-to-Harvest consumer API by default; GoFurry backend is the caller. Restrict response body sizes, avoid unbounded list/history queries and do not return unredacted raw URL/query strings.

Health endpoints:
- `GET /livez` — process/liveness, no secret detail, 200 when event loop can respond.
- `GET /readyz` — dependency/readiness appropriate to runtime mode; 503 when DB/control dependency unusable or draining; provider upstream 429 and an optional offline remote Worker must not fail Server readiness.
- `harvest healthcheck --config config.yaml` — read-only built-in local readiness probe, usable as Docker HEALTHCHECK and LibreCosta Uptime target.

Set `Cache-Control: no-store` for authenticated operational endpoints. Log only allowlisted route template, request ID, status, duration, job/attempt UUID and safe Provider/Capability codes; no request body, credentials, URLs with tokens or proxy endpoints.

## 7. Runtime lifecycle, Task, Docker/Compose and release

### Runtime and Fiber

One runtime owner: validate YAML -> initialize logging/provider registry/secret policy/egress clients -> open Postgres -> check migrations compatibility -> construct scheduler/quota/worker -> register HTTP routers and hooks -> listen -> mark ready (Fiber `OnListen` after dependencies ready). Keep jobs disabled until result submission API is available.

SIGTERM: set readiness false, stop new schedule/claim/permits, allow bounded in-flight lease renewals and result commits while private API still serves, then cancel overdue local work, call Fiber graceful `ShutdownWithContext` (with `OnPreShutdown` and `OnPostShutdown` idempotently enforcing cleanup), finally close proxy transports/DB. Startup/listen failure rolls back resources in reverse order even if Fiber hooks never run. No prefork.

### Task interface

```text
task install
task dev                 # foreground, server + local worker
task dev:worker          # independent worker, explicit config
task start               # owned background or foreground (document precisely)
task stop                # verifies current-checkout process identity
task build
task test
task check
task sql:generate
task sql:check
task migrate ACTION=status|up
task check:docker
task check:containers    # isolated mock/test project; never touches production
```

All call the one required YAML, use `GOTOOLCHAIN=go1.27.3` or pinned project toolchain and work on Windows/Linux without a PowerShell-only task. No `.env` runtime loading or environment field overrides. `task stop` must never kill an arbitrary PID found at a port; only a verifiably owned process/container or safely report no tracked process. Migration is explicit and cannot modify production implicitly.

### Docker and deployment

- Multi-stage build, pinned Go toolchain, nonroot distroless (or equivalent minimal runtime with proper CA roots and time zone support), `ENTRYPOINT harvest`, `CMD serve --config /etc/harvest/config.yaml`, built-in healthcheck, graceful SIGTERM and realistic `stop_grace_period`.
- GHCR release images tagged immutable semver and commit SHA; Linux amd64/arm64. No `latest`-only operational deployments. Record checksums and release notes, avoid meaningless verification spam.
- Production Compose: one Harvest container referencing **existing** PostgreSQL 18 with an independent Harvest database, mount ignored host `config.yaml` read-only; do not start another PostgreSQL just because Compose is used. Bind only to loopback/Tailscale/private interfaces, never expose `/internal/v1` publicly. Worker can be another instance of the same image with `worker` subcommand.
- A separate disposable integration Compose may start its **own isolated** PG18 and mocked upstream/proxy for test only. Never reset or prune real dev/prod databases during checks.
- Configure DB max connections, Worker concurrency, HTTP timeout, response memory, WAL/retention budgets and proxy transport idle limits explicitly. Avoid a log-heavy or healthcheck-heavy idle process. Container logs rotate with modest size and count.

### Backups and compatibility

Goose migrations are reviewed, single-owner, and applied before new service startup. Never silently revert a destructive migration with a fake Down. Backup and fresh/upgrade-path tests must precede production schema changes. Worker protocol and Provider result schema advertise compatibility versions: incompatible Worker cannot claim Jobs; upgrade Control/Worker in documented sequence. Persisted Job requests remain executable through supported schema migration, or are safely rejected with operator diagnostics; do not reinterpret historical payloads.

## 8. Acceptance and resource budget

Tests use disposable PostgreSQL 18, two independent worker runtimes, an in-process mocked Web/Steam source, a fake HTTP/SOCKS5 proxy and deterministic clock. Live internet/Steam credentials are **optional** manual verification and never CI prerequisites.

Required gates:
1. Fresh migration and idempotent upgrade path, SQLC generated source reproducible, every required query tested with transaction races and `EXPLAIN` on sample volume.
2. Two Workers racing one Job yield one current lease; stale-fence completion and cancelled-work submission are rejected; identical post-commit HTTP retry gets same receipt.
3. Quota across two workers never exceeds configured account/egress bucket; proxy fallback follows explicit policy; loss of control server fails closed for new requests.
4. Same request submitted through differing JSON key order/whitespace maps to one canonical active identity; authorization namespace prevents cross-consumer dedupe.
5. A valid Steam scope updates with another scope failing, preserving prior good data; real zero players remains zero; unchanged details do not flood history.
6. Concurrent result transactions in the same stream cannot expose position N+1 before N commits. Rollback cannot leave committed cursor gaps. Retention never silently skips events.
7. Consumer falls behind log retention -> explicit `cursor_expired` 410; baseline + concurrent update/delete + replay converges correctly; consumer ACK does not precede local commit.
8. Bounded pruning removes old attempts, receipts, snapshots and samples without touching active leases, latest-good, required stream events or important current identities; storage pressure is measurable.
9. Fiber clean startup, bind failure/DB failure rollback, Graceful Shutdown with in-flight remote result completion, and forced grace expiry recovery; `/livez` and `/readyz` are correct.
10. Task dev/start/stop/build/check and Docker image/Compose probes work independently; no accidental production DB operation or ambient environment proxy/key leaks.
11. With conservative starting parameters on a shared-size 4C8G test target, measure idle CPU, heap, connection count, heartbeat/poll DB queries, write amplification, database/WAL growth, API p95 and cleanup batch cost. Record actual results and tune before claiming a scale or SLA.
12. No consumer can list private targets/observations or Worker endpoints without proper scope; bound pagination/body size and SSRF-aware proxy transport are exercised.

A1-C **does not** authorize automatic deployment, ingestion into the real GoFurry database, data migration from legacy GoFurry, or new user identity services.

## 9. Implementation handoff (after contract review)

Proposed implementation ordering:
- V0.1-A0: Go repo governance, Cobra/YAML/Task/Fiber Router/health/runtime lifecycle, Docker skeleton, SQLC/Goose and disposable PG integration harness.
- V0.1-A1: Target/Provider discovery, request validation, Schedules/Jobs/Attempts, two-Worker control and fencing acceptance.
- V0.1-A2: Egress/quotas with fake HTTP/SOCKS5 proxies, direct/prefer/require policies and multi-worker request-permit checks.
- V0.1-A3: Current results, scoped Observation, serialized change stream, reset/ACK/bounded retention and consumer integration.
- V0.1-B: Web Provider proof; V0.1-C: steam-go provider proof; V0.1-D: operations hardening, measured budget and GoFurry CN consumer proof.

Use focused Issues/PRs on `develop`; no speculative multi-repo refactor. Any change to `gofurry/steam-go` needs its own compatible PR after a proven integration gap.
